## 1. 架构概览

本地单机工具：浏览器里的操作台只管展示与操作；本机 Python HTTP 服务负责读写用例文件、保存环境、编排跑批、把请求打到被测系统并用判定条件核对，再把结果写入历史。分层为「操作台前端 → 本地控制服务 →（用例仓库 / 环境配置 / 执行引擎 / 跑批历史）」，执行引擎只出站调用被测网关或服务，不反向依赖业务仓代码。

## 3. 技术选型

| 决策项 | 选了什么 | 服务的能力 | 为什么不选另一个 | 以后再改的成本 |
|---|---|---|---|---|
| 运行时形态 | 静态页 + 本机 Python HTTP 服务（对齐 PERF 压测台） | C09 C11 | 不选独立 SPA 构建链：PRD 要求对齐全静态 `leidian-perf-web/web`，引入构建链无法直接复用其面板/标签页资产 | 贵 |
| 用例持久化 | 模块目录下的 YAML/JSON 文件 | C10 C01 C02 | 不选数据库：INTENT/PRD 要求用例进 Git 与功能版本一起改，库表不利于同仓 diff | 便宜 |
| 出站调用 | 服务端代发 HTTP（带登录凭证） | C11 C06 | 不选浏览器直连被测接口：易受跨域限制，且登录凭证不宜只放在前端 | 便宜 |
| 判定方式 | 声明式判定条件（状态码与字段期望） | C02 C04 C11 | 不选用例内嵌脚本：首期规则/压住预警接口断言以字段核对为主，嵌脚本会提高维护成本且无性能脚本需求 | 便宜 |
| 历史存储 | 每次跑批一份结果文件 | C05 | 不选只保留内存：验收要求重启后仍能回看历史跑批 | 便宜 |

## 4. 关键数据流

| 路径 ID | 数据从哪来 | 经过模块 | 存到哪 |
|---|---|---|---|
| P01 | 操作台录入的用例内容 | 操作台前端 → 本地控制服务 → 用例仓库 | 用例文件 |
| P02 | 环境表单 + 勾选的用例 | 操作台前端 → 本地控制服务 → 环境配置 → 用例仓库 → 执行引擎 → 跑批历史 | 跑批历史文件；界面展示逐条结果 |
| P03 | 内置预警规则用例包 + 环境 | 操作台前端 → 本地控制服务 → 用例仓库 → 执行引擎 → 环境配置 | 跑批历史；被测系统产生业务副作用 |
| P04 | 内置压住预警用例包 + 环境 | 操作台前端 → 本地控制服务 → 用例仓库 → 执行引擎 → 环境配置 | 跑批历史（含跳过原因） |
| P05 | 已落盘的跑批记录 | 操作台前端 → 本地控制服务 → 跑批历史 | 仅读取，不新增 |
| P06 | 静态样式与页面结构 | 操作台前端 | 无业务持久化 |

## 5. 额外结构与假设

| 加了什么结构 | 为了解决什么情况 | 这种情况的依据 | 以后再改的成本 |
|---|---|---|---|
| 用例跳过标记 | 压住预警接口尚未提供时，整包执行若一律当失败会淹没真实失败 | 「有通过/失败，或明确跳过原因」 | 便宜（改用例元数据与结果枚举） |
| 步骤间取值引用 | 新建规则后再启用/删除必须带上新建返回的 id，否则串不成完整流程 | `WarnRuleController.java`（create 返回含 id，enable/delete 路径依赖 id） | 便宜（约定占位符语法） |
| 同时只跑一批 | 连点两次执行时两批日志与结果写进同一展示区会分不清 | `leidian-perf-web/web/server.py`（Job 状态与单任务展示） | 便宜（去掉互斥即可并行） |

## 6. 关键选型与代价（请重点核对）

### 运行时形态

- **选了什么**：静态页 + 本机 Python HTTP 服务
- **依据**：PRD/INTENT 要求 UI 基线为 `leidian-perf-web/web`；该类比为同构本地操作台
- **做错的代价**：若改成 Node/Java 服务或强制 SPA 工程，需重写本地服务与页面集成，历史/用例 API 也要迁一次
