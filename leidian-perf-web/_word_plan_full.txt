[10] 雷电系统数据库性能测试开展方案
[2] 工作目标
本次性能测试用于验证雷暴过程业务在 PostgreSQL 数据库中的建模、写入、分区、索引、时序查询、空间查询等能力本次性能测试用于验证雷暴过程业务在 PostgreSQL 数据库中的建模、写入、分区、索引、时序查询、空间查询等能力。
本次测试需要回答以下问题：
表结构是否能承载雷暴过程、设备监测、闪电监测、预警、告警、工况联动、巡检、隐患、维修等多域数据。
高频时序数据是否适合按时间分区，分区粒度是否合理。
经纬度数据如何生成才接近真实业务，空间查询是否需要PostGIS。
按当前测试机可承载的数据规模造数后，写入、分页、曲线、统计查询是否存在明显性能风险。
在 S0 建模验证档、S1 基线档、S2 增长档、S3 压力档、S4 推荐存量档几个阶段中，明确各阶段造数规模、测试场景和阶段结论。
[3] 测试定位与边界
本次测试定位为前期数据库性能摸底测试，主要用于验证PostgreSQL路线下雷暴过程业务的数据建模、分区策略、索引策略、写入能力、时序查询能力、空间查询能力和典型统计查询能力。
本次测试结论用于支撑:
数据库表结构优化。
索引优化。
分区策略调整。
后续正式环境容量规划。
正式压测方案制定。
确认当前数据库设计是否存在明显方向性风险。
本次测试不作为生产环境最终验收结论。
本次测试不覆盖以下内容:
不覆盖正式生产环境容量验收。
不覆盖Kafka集群吞吐上限验证。
不覆盖WebSocket / 3D推送性能验证。
不覆盖PostgreSQL高可用、主从切换、故障恢复能力验证。
不覆盖国产数据库性能结论。

SELECT count(*) AS lightning_count
FROM thunderstorm_process p
JOIN mine_site m
ON m.mine_code = p.mine_code
JOIN biz_lightning_event l
ON l.strike_time BETWEEN p.strike_start_time AND p.strike_end_time
AND l.lightning_point IS NOT NULL
AND ST_DWithin(
l.lightning_point,
m.dispatch_room_point,
50000
)
WHERE p.id = :process_id;

SELECT p.id,
count(l.id) AS lightning_count,
count(CASE WHEN l.source_type = 'CMB' THEN 1 END) AS cmb_count,

ON m.mine_code = p.mine_code
LEFT JOIN biz_lightning_event l
ON l.strike_time BETWEEN p.strike_start_time AND p.strike_end_time
AND l.lightning_point IS NOT NULL

l.lightning_point,
m.dispatch_room_point,
50000
)
GROUP BY p.id
ORDER BY p.id;

SELECT p.id,

[3] 阶段推进原则
当前阶段数据校验未通过，不进入压测。
当前阶段压测未完成，不进入下一阶段。
当前阶段出现明显慢 SQL，应先分析执行计划，再决定是否继续扩容。
当前阶段磁盘使用率超过 80%，停止继续扩容。
当前阶段如果数据库连接池耗尽、锁等待严重或错误率明显异常，应暂停测试并定位原因。

高频时序数据是否适合按当前粒度分区。
闪电类空间查询是否需要继续保留 PostGIS。
哪些 SQL 或业务场景需要优化。
正式环境压测前还需要补充哪些测试。
当前测试结果不作为生产最终验收结论。
建议报告结论示例：
本次测试基于 14核cpu、32GB 内存、1TB 硬盘的单机环境开展，测试结果用于前期数据库建模、索引、分区和查询性能摸底。
在当前硬件条件下，测试结论仅反映单机测试环境中的性能表现，不代表正式生产环境性能上限，也不作为最终生产验收结论。
如需验证推荐存量 S4 或更高并发场景，应在更接近正式部署的数据库服务器上补充测试。
