## ADR-001A：纯前端静态方案 + localStorage

### 决策
采用 **HTML/CSS/原生 JS + localStorage** 的纯前端静态单页方案，无后端、无部署环节。

### 备选方案
1. **前后端分离（后端 API + 数据库）**：支持云同步/多用户，但超出 MVP 本地存储范围，引入大量交付与运维成本。**否决**。
2. **引入前端框架（React/Vue）**：组件化虽好，但需构建链与依赖，对「零待办列表 + 零部署」的 MVP 属过度设计。**否决**。
3. **本地文件存储（IndexedDB/File System API）**：IndexedDB 容量更大但不需异步事务复杂度；MVP 数据量小，localStorage 足够。**否决（保留替代）**。

### 代价
- 容量上限 ~5MB、单浏览器隔离、无跨页同步、清缓存即丢——均为 PRD 已声明的非目标边界。
- 采用原生 JS 无框架，后续若需扩展（如排序/分类）代码组织成本略增，但 MVP 规模可接受。

### 理由
- 完美契合「本地存储」目标与最小交付成本；零后端、零部署，浏览器直接打开即用。

## ADR-001B：数据层抽为纯 JS 模块 + 可注入存储适配器

### 决策
`store.js`（数据层）为**不依赖 DOM、不依赖浏览器全局对象**的纯 JS 模块；对 localStorage 的访问通过**可注入的存储适配器**（默认真实 `localStorage`，测试注入内存 mock）。

### 备选方案
1. 数据层直接使用 `window.localStorage`：实现快，但无法在 Node 单测，测试需浏览器环境。**否决**。
2. 引入完整测试框架（如 Vitest/jsdom）：能测渲染层，但引入构建/依赖，违背零依赖目标。**否决（可选增强）**。

### 代价
- 需在 `store.js` 中多一层存储适配器抽象（约一个小接口），成本极低。

### 理由
- 以最小代价换取数据层可在 Node 直接单测，满足 PM「数据层必须可测」要求，同时保持零构建、零部署。

## ADR-001C：单一存储键 `todo.items` + 全量覆盖写

### 决策
以**单一键** `todo.items` 存整份数组 JSON，每次变更全量 `setItem` 覆盖。

### 备选方案
- 每条待办一个键 + 索引键：粒度细但需维护一致性/索引，复杂；多键故障面大。**否决**。

### 代价
- 全量读写；当数据量极大时（远超 MVP 预期）有写放大。MVP 数据量小，可接受。

### 理由
- 数据量小、结构简单，一次读写即完成整份持久化，避免多键一致性问题。

## ADR-001D：显式排除项

明确排除：后端 API、构建工具链、前端路由、跨页实时同步、云同步、多用户。均为 PRD 非目标，防止范围蔓延；如后期需要，另开迭代并重新评估架构。
